# Ponytail Review — Рев'ю на надлишкову складність (Over-Engineering)

Цей скіл спеціалізується на перевірці змін (git diff, PR, окремих файлів) з метою скорочення кодового обсягу та усунення зайвої складності.

Найкращий результат після цього рев'ю — **скорочений diff та чистіша кодова база**.

---

## 📋 Формат результатів

Один рядок на кожне зауваження у форматі:
`L<номер_рядка>: <ТЕГ> <що саме скоротити/видалити>. <альтернатива / заміна>.`  
або `<шлях_до_файлу>:L<номер_рядка>: ...` для багатофайлових змін.

### Теги класифікації:

- **`delete:`** Мертвий код, непотрібна надлишкова гнучкість, спекулятивна фіча "про запас". *Заміна:* видалити без заміни.
- **`stdlib:`** Власноруч написаний велосипед, який уже є в JS/TS/Node.js/Web API (`Intl`, `crypto.randomUUID`, `Array.prototype.*`, `URL`). *Заміна:* вказати функцію stdlib.
- **`native:`** Стороння бібліотека чи складний кастомний код для того, що браузер вміє нативно (`<dialog>`, `<input type="date">`, `inert`, CSS grid/flex). *Заміна:* нативний елемент/атрибут/CSS.
- **`reuse:`** Дублювання логіки, яка вже є в існуючих утилітах або компонентах проєкту (`cn()`, спільні модалки/гріди/хуки). *Заміна:* імпорт наявного хелпера.
- **`yagni:`** Абстракція з однією реалізацією, конфігурація, яку ніхто не налаштовує, шар адаптера з одним викликачем. *Заміна:* прямий спрощений виклик.
- **`shrink:`** Та сама бізнес-логіка, але в меншу кількість рядків (без втрати читабельності). *Заміна:* лаконічний вираз.

## 🎯 Чекліст перевірки diff'у

1. [ ] Чи можна скоротити цей diff на 30–50% без втрати функціональності?
2. [ ] Чи не створено новий стан/хук/ефект там, де значення можна просто обчислити синхронно під час рендеру (derived state)?
3. [ ] Чи не встановлено новий npm-пакет?
4. [ ] Чи не здубльовано існуючі утиліти/стилі?
5. [ ] Чи збережено валідацію, RLS, типізацію та доступність (a11y)?
