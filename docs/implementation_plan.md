# План: готові коментарі для батьків і збереження даних

request_feedback: false
status: реалізовано локально; потрібна перевірка на PHP-хостингу

## Мета

Після вставлення готових текстів із чатів учитель бачить їх у списку учнів і копіює потрібний текст одним натисканням біля імені. Додавання будь-яких даних на PHP-хостингу має давати достовірний статус запису й не губити зміни за швидких або паралельних дій.

## Поточний стан

- `savedReports` уже зберігає текст за ключем `studentId:period`; кнопка копіювання є лише в центрі звітів для вибраного періоду. На іншому тижні попередній текст не видно.
- У табличному й картковому журналі біля імені учня немає дії для копіювання готового звіту.
- Пакетний імпорт показує успіх до підтвердження запису сервером.
- `updateDbAndSave` може запускати кілька записів паралельно з одного стану React. `saveDatabase` робить окремі GET і POST, тому перевірка версії не атомарна. Публічний фідбек змінює той самий JSON-файл.
- У `api.php` після невдалого `rename` запасний `file_put_contents` не перевіряється, але функція повертає успіх.
- Точний збій на хостингу ще не відтворено; відомо лише, що він виникає на PHP-хостингу. Текст помилки потрібен для вибору конкретного виправлення.

## Етап 1 — імпорт і доступність готових коментарів

1. Залишити наявну схему `SavedReport`; для відображення отримувати всі звіти учня, сортувати за `updatedAt`, показувати період і дату. Старі звіти мають бути доступні незалежно від активного періоду.
2. У табличному та картковому журналі поставити біля імені учня видиму кнопку «Скопіювати коментар», якщо є збережений текст. Одне натискання копіює найновіший звіт; у підказці вказати період. Якщо звітів кілька, старі доступні в картці/центрі звітів.
3. Після пакетного імпорту показати учнів зі статусом розпізнавання і збереження. Кнопка копіювання доступна прямо в результаті імпорту; toast успіху — лише після підтвердження сервера.
4. Не перезаписувати наявний звіт за тим самим періодом непомітно: показати попередження/порівняння перед заміною. Якщо текст змінено після позначки «Надіслано», явно визначити статус нового тексту.
5. Не записувати неоднозначне зіставлення імен автоматично; дати вчителю вибрати учня для такого блоку.

**Критерії приймання:** збережений минулого тижня коментар знаходиться за ім'ям; копіювання біля імені працює в обох видах журналу; скопійований текст точно відповідає показаному періоду; невдале збереження не показує «Збережено»; неоднозначний блок не прив'язується до іншого учня.

## Етап 2 — діагностика синхронізації

1. Отримати точний toast, HTTP-статус і відповідь запитів `GET/POST api.php` під час помилки; за можливості — рядок із PHP error log без приватних даних учнів.
2. Відтворити окремо: одиничне додавання, кілька швидких дій учителя, зміна з двох вкладок, учнівський фідбек одночасно з дією учителя, відмову запису в `data/`.
3. Зафіксувати першопричину для кожного сценарію. Не об'єднувати `401`, `409`, мережеву помилку та `500` в один статус.

**Критерій виходу:** для повідомленої користувачем помилки відомі точні кроки, HTTP-відповідь і шар, де збій починається.

## Етап 3 — надійне збереження

1. Зробити одну послідовну чергу записів у клієнті; кожна наступна зміна має будуватися на найновішому стані, а не на старому замиканні `db`.
2. Зробити перевірку ревізії та запис на PHP-сервері однією захищеною операцією. Публічне збереження фідбеку має користуватися тим самим правилом блокування файлу, щоб не втрачати зміни вчителя або учня.
3. Повернути успіх лише після фактично успішного запису; якщо `rename` і запасний запис не спрацювали, відповідь повинна бути помилкою сервера.
4. Показувати різні toast для конфлікту, завершення сесії, мережі та відмови диска. При конфлікті зберігати локальні незаписані зміни для відновлення, не підтверджувати їх як серверні.

**Критерії приймання:** швидкі послідовні дії не гублять дані; дві вкладки не можуть тихо перезаписати одна одну; одночасний фідбек учня не губиться; помилка диска не дає хибного успіху; після перезавантаження підтверджені зміни присутні в JSON.

## Перевірка

- Тести чистої логіки: вибір найновішого звіту, історія за періодами, неоднозначні імена, повторний імпорт.
- Перевірка збереження: швидкі зміни, паралельні вкладки, паралельний публічний фідбек, конфлікт і відмова запису.
- Ручна перевірка UI на широкому й вузькому екрані, з клавіатури, з українськими toast.
- Обов'язкові команди після змін: `npm run typecheck`, `npm run lint`, `npm run test`, `npm run build`.
- Перед розгортанням: резервна копія бойового `data/database.json`; перевірка на тестовому PHP-середовищі. Розгортання — окремий крок.

## Відкриті рішення

- Потрібен точний текст помилки на PHP-хостингу, щоб підтвердити першопричину.
- За замовчуванням кнопка біля імені копіює найновіший збережений звіт; це рішення вже реалізовано.

## Додатковий запит: бонуси KP

Користувач підтвердив реалізацію кодом. Замість тижневого модального вікна створено окрему сторінку `#/kp` з вибором кількох класів, навігацією по тижнях та довільними датами. Нарахування діє на всіх вибраних учнів; є індивідуальне значення та спільне значення «Всім по». На сторінці окремо доступні баланси учнів і повна історія з пошуком та фільтром за періодом. Точне повторне нарахування за той самий період блокується ключем періоду; старі тижневі ключі збережено.

## Стан перевірки

- Локальні `typecheck`, `lint`, `test`, `build` виконуються після завершення змін.
- Синхронізація перевірена автоматичними тестами черги збережень, конфлікту ревізій і серверних помилок. Фактичний PHP-хостинг та його журнали наразі недоступні, тому першопричина повідомленої помилки ще не підтверджена.
- Розгортання на хостинг не виконувалось.
