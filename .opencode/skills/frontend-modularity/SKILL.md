# Frontend Modularity (уроки з рефакторингу workbench)

Цей скил кодифікує причини, через які довелося рефакторити модуль `workbench`, щоб новий код писався одразу правильним. Якщо код, який ти пишеш, порушує ці правила — він приречений на рефакторинг.

## 1. Чиста логіка — поза компонентами, в окремий `.ts` модуль з тестами

Будь-яка нетривіальна чиста функція (аналіз тексту, генерація, трансформація, підрахунок) належить **окремому модулю** типу `*.ts`, а не тілу `.tsx` компонента.

- Погано: 100-рядкова функція `analyzeUkrainianWordPhonetics` всередині `InteractivePhonetics.tsx`.
- Добре: `phonetics.ts` + `phonetics.test.ts`, компонент лише імпортує.

Правила:
- Функція без JSX та React-хуків → `.ts` файл поряд з компонентами (одна тема на файл: `aiTextGenerator.ts`, `textUtils.ts`, `tokenUtils.ts`).
- Кожен новий чистий модуль логіки → обов'язковий `*.test.ts` (vitest) з покриттям ключових гілок. Це фіксує поведінку та робить рефакторинг безпечним.
- Компонент залишається "тонким": тільки стан, рендер та колбеки.

## 2. Спільні JSX-патерни → спільний компонент, не копіювати

Якщо однаковий JSX-патерн (грід, пікер, таблиця, модалка) зустрічається у 2+ місцях — винеси у спільний компонент зі слотом (`renderWord`/`children`/пропси для конфігурації).

- Приклад: три Interactive-компоненти копіювали грід токенів з лічильником `wordIdxCounter` та розділовими знаками → спільний `TokenTextGrid` з пропом `renderWord`.
- Сигнал: бачиш `wordIdxCounter`, `tokens.map` з `if (!token.cleanWord)`, повторені класи `inline-flex ... gap-0.5` у 3 файлах — це вже спільний компонент.
- Спільний компонент — це не тільки менше коду: це єдине місце виправлення бага (наприклад, стилю розділових знаків) і консистентність.

## 3. Константи, конфіги та regex — єдине джерело істини

- Регулярний вираз або літеральний рядок, який використовується в кількох місцях, → одна експортована константа в спільному модулі. Не дублюй regex-літерали по компонентах (приклад: `UKRAINIAN_WORD_REGEX` був 5 разів, тепер один у `phonetics.ts`).
- Статичні конфіги (списки режимів, правил, стилів) → окремий `.ts` модуль (`workbench.modes.ts`, `constants/morphologyConstants.ts`), а не всередині компонента.
- Літерали, що пов'язані (назва режиму ↔ його label/стиль), тримай в одній структурі даних + фабрика getter (`getModeLabel`), а не окремими розрізненими мапами.

## 4. Межі розміру файлу

- `.tsx` файл > ~300 рядків — стоп-сигнал: розбивай на компоненти та хук.
- `.ts` модуль, що перевищує одну відповідальність → розділяй за темами.
- Якщо компонент має кілька різних UI-блоків (модалки, панелі, таблиці) — винось кожен блок у свій файл у `components/`, а сторінка лише композиціонує.

## 5. Одна відповідальність на файл

- `*.api.ts` — тільки запити (query/mutation обгортки).
- `*.types.ts` — тільки типи.
- `*.constants.ts` / `*.modes.ts` — тільки конфіги.
- Компонент — тільки рендер + локальний стан.
Змішування типів, запитів, конфігів і JSX в одному файлі — головний драйвер майбутнього рефакторингу.

## 6. Не створюй дублікат "на майбутнє"

- Якщо патерн повторюється вже в 2-му місці — винось одразу, не чекай 3-го.
- Якщо логіку можна винести в чисту функцію без болю — винось одразу з тестом.
- "Мені ще треба буде" — НЕ привід копіювати. Це привід винести спільне.
