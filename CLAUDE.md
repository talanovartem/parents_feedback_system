# Проєкт parents_feedback_system — інструкції для ШІ-агентів

> Усі агенти діють за єдиною **Конституцією** у [`.spec/constitution.md`](file:///.spec/constitution.md).
> Цей документ — швидкий довідник.

## Ключові джерела

| Джерело | Що містить |
|---|---|
| `.spec/constitution.md` | **Вищий закон** проєкту: українська мова UI, toast-сповіщення, локальний JSON-рушій, Ponytail (економія коду), 4-крокова перевірка. |
| `.agents/skills/` | Навички — `*.SKILL.md` (ponytail, ponytail-review, bmad-agile-workflow, spec-driven-development, frontend-modularity, testing-vitest тощо). |
| `kasetto.yaml` | Декларація project-scope sync: Antigravity, OpenCode, Cline, Claude Code, Cursor. |

## Як працювати

1. **Мова UI** — виключно українська (`.spec/constitution.md`, 1.1).
2. **Сповіщення** — лише **toast** (Sonner); жодних червоних/зелених текстів під формами.
3. **Економія коду (Ponytail)** — дотримуйся драбини рішень (`.agents/skills/ponytail/SKILL.md`). Видалення коду завжди краще за додавання. Жодних надлишкових бібліотек та абстракцій.
4. **Брейншторм та архітектура** — при появі нових великих функцій спершу проводити обговорення вимог (`/grill-me`), формувати специфікацію перед кодуванням (`bmad-agile-workflow`).
5. **4-крокова перевірка після змін**:
   - `npm run typecheck`
   - `npm run lint`
   - `npm run test`
   - `npm run build`
6. **Обов'язкова зупинка після планування або для уточнення** (`.spec/constitution.md`, Стаття 5):
   - Попри будь-які дозволи на зміни або політики автосхвалення інструментів, агент **ЗОБОВ'ЯЗАНИЙ ЗУПИНИТИСЯ** після створення плану, генерації ідей чи для уточнення вимог.
   - Заборонено автоматично починати кодування чи змінювати файли без явного текстового підтвердження користувача у чаті (наприклад, «починай», «роби», «погоджую»).

# 📜 КОНСТИТУЦІЯ ПРОЄКТУ PARENTS-FEEDBACK-SYSTEM

> **Статус:** Дійсна & Обов'язкова  
> **Версія:** 1.0  
> **Джерело правди:** `.spec/constitution.md`  

Цей документ є вищим технічним та продуктовим законом проєкту **parents-feedback-system**. Усі розробники та ШІ-агенти зобов'язані беззастережно дотримуватися цих правил при виконанні будь-яких задач.

---

## 🏛️ СТАТТЯ 1: UI, UX ТА МОВНІ СТАНДАРТИ

1.1. **Мова інтерфейсу:** Усі тексти, назви, підписи, ярлики та сповіщення в користувацькому інтерфейсі (UI) повинні бути **виключно українською мовою**.  
1.2. **Система сповіщень:** Усі сповіщення про успішні дії або помилки потрібно виводити у вигляді **Toast-повідомлень** (Sonner). Локальні червоні/зелені текстові написи під формами слід уникати для кращого UX.  
1.3. **Естетика та ергономіка для вчителя:** Дизайн повинен бути чистим, швидким та зручним для швидкого виставлення оцінок (0-12) без зайвих кліків, із виразним колірним кодуванням оцінок та адаптивним журналом.

---

## 🗄️ СТАТТЯ 2: ДАНІ ТА ЛОКАЛЬНЕ СХОВИЩЕ (JSON)

2.1. **Автономність без зовнішньої БД:** Додаток працює локально. Основним сховищем даних є файл `data/database.json`.  
2.2. **Надійність збереження:** При кожній зміні оцінки, коментаря або учня дані зберігаються в JSON-файл через локальний API та дублюються в браузерний `localStorage` як аварійний кеш.  
2.3. **Цілісність структури:** Усі сутності (класи, учні, уроки, критерії 0-12, поурочні записи та примітки) суворо типізуються за допомогою TypeScript interfaces.

---

## ⚡ СТАТТЯ 3: ПРОДУКТИВНІСТЬ, МОДУЛЬНІСТЬ ТА ЕКОНОМІЯ КОДУ

3.1. **Модульність коду:** Новий код пишеться модульним згідно з `.agents/skills/frontend-modularity/SKILL.md`:
   - Чиста логіка (розрахунок середніх балів, фільтрація, форматування звітів для ШІ) виноситься у `.ts` модулі з тестами.
   - Компоненти розміром понад ~300 рядків декомпозуються на підкомпоненти.
3.2. **Мінімалізм та запобігання оверінжинірингу (Ponytail Ladder):**
   - Дотримуватися принципу «Найкращий код — це код, який ви не писали» за `.agents/skills/ponytail/SKILL.md`.
   - Жодних надлишкових бібліотек та спекулятивних абстракцій. Простота перемагає складність.

---

## 🧪 СТАТТЯ 4: АВТОМАТИЧНА ВЕРИФІКАЦІЯ (4 КРОКИ)

Після будь-яких змін до коду агент зобов'язаний виконати 4-крокову верифікацію:
1. `npm run typecheck` — 0 помилок типів.
2. `npm run lint` — 0 помилок та критичних попереджень лінтера.
3. `npm run test` — усі тести мають проходити успішно.
4. `npm run build` — збірка проєкту має завершуватися з кодом 0.

Якщо будь-який крок падає, зупинитись і виправити проблему до завершення роботи.

---

## 🛑 СТАТТЯ 5: ОБОВ'ЯЗКОВА ЗУПИНКА ПІСЛЯ ПЛАНУВАННЯ ТА ДЛЯ УТОЧНЕННЯ

5.1. **Заборона автовиконання без підтвердження:** Попри будь-які дозволи системи чи політики автосхвалення (auto-approve/review policy), агент **ЗОБОВ'ЯЗАНИЙ ЗУПИНИТИСЯ** після етапу планування, генерації концепцій або запитань до користувача.
5.2. **Пряме підтвердження від користувача:** Переходити до кодування або реалізації дозволено **виключно** після отримання явного підтвердження в текстовому повідомленні від користувача (наприклад: «починай», «роби», «погоджую», «виконуй»).
5.3. **Режим консультації / дизайну:** Якщо користувач просить придумати, продумати форму, запропонувати варіанти або зупинитися на плані — агент повинен виключно обговорити ідеї, зафіксувати план у документації та **завершити хід без внесення змін до коду**.
